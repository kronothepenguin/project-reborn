# Working tasks

A slave works one task and reports to its master. The master and the user decide.

A task is a task file, or a brief in the slave's prompt for work without behaviours. The brief stands in for the task
file: its goal for `# Goal` and `# Steps`, its scope for `scope`, its skills for `skills`, its checks for `# Checks`, and
its slug for `<feature>-<NN>`. With a brief, step 1 reads the brief and loads its skills, and steps 4 and 7.1 are
skipped.

The work goes in two reports: ready, then delivered. The slave ends its turn only to report one of them, and waits for
each long check in the foreground.

## 1. Read

Read the task file, the feature's `spec.md` and `plan.md`, and each file under `# Context`. Load each skill in
`skills`. The task's `# Goal` names the behaviours of `spec.md` it implements.

## 2. Worktree

The worktree and the branch are both named `<feature>-<NN>`, from the task's feature folder and number:

```sh
git worktree add -b <feature>-<NN> .claude/worktrees/<feature>-<NN> main
```

Work there.

## 3. Steps

Do the steps of `# Steps`. Change only the folders in `scope`.

## 4. Tests

Write one test per behaviour that `# Goal` names, with the `testing-behaviours` skill.

## 5. Focused tests

While it builds, run the tests of the code it changes and the one browser suite its change touches:

```sh
go test ./...                                                  # in the changed package, or its pnpm test script
node --disable-warning=ExperimentalWarning run.mjs <suite>     # inside tests/e2e
```

A failing test starts a review of the code, with the `testing-behaviours` skill. Work that changes documents alone runs
the knowledge check alone.

## 6. Knowledge

Update the knowledge files the change makes stale, in the project's own `knowledge/` folder.

## 7. Ready

Run each command on its own and read its result before the next.

1. Delete the task file.
2. Commit with a one-line title that starts with `feat:`, `fix:`, `refactor:` or `docs:`. Stage explicit paths.
3. Keep the branch and the worktree. Report the work ready, in the shape of step 9.

## 8. Deliver

At its turn, the master's message, run in the worktree, each command on its own:

1. `git rebase main`. Resolve each conflict, `git add` the file, then `git rebase --continue`. On a conflict in a
   generated `index.md` (it starts with `<!-- generated by index.py -->`), take either side, run `index.py` of the
   `documenting-with-okf` skill with no argument and add the result. Resolve the lines of the spec and the plan so both
   sides' lines stay.
2. Run the commands under `# Checks`. For each project changed, list its dependants with
   `make dependants project=<folder>` at the root, and run `make -C <folder> check` in the project and in each
   dependant.
3. Run `make e2e` at the root once, in the foreground. Work that changes documents alone skips it and runs the
   knowledge check: `python3 -I .agents/skills/documenting-with-okf/scripts/check.py`.
4. Fix what breaks and commit the fix.
5. Report the work delivered, with the branch's last commit. The master fast-forwards `main` and removes the branch
   and the worktree.

A conflict or a failure the master sends back is fixed the same way, then reported delivered again.

## 9. Report

Report to the master, in this shape:

```markdown
State: <ready or delivered>, <branch>, <last commit>
Changed: <what changed, by path>
Tests:
- <test name>: <behaviour of spec.md it proves>
Checks:
- <command>: <pass or fail, with the failure>
Where the code contradicted a source:
- <source>: <what the code does instead>
Facts for other tasks:
- <fact>: <the task or feature it serves>
Open questions:
- <question>
```

## Open questions

A question that the task or the brief, the spec and the plan leave open stops the work: report it, and the master
asks the user.
