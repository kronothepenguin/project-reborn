# Research: CMS Web Application

**Feature**: `014-cms-web-app` | **Date**: 2026-09-12

Phase 0 output. Every decision below resolves an open point in the plan's Technical Context or a spec requirement whose implementation shape was not fixed by the specification. Decisions are binding for the plan; alternatives are recorded so later features can revisit them deliberately.

---

## R1 — Store file families named by domain; adapter lives in the CMS

**Decision**: Add this feature's structures to the shared store under domain-named families — `users` (`users` table), `sessions` (`sessions`), `recovery-tokens` (`recovery_tokens`), and `login-attempts` (`login_attempts`) — and implement the seven `packages/auth` persistence interfaces in a CMS-internal adapter, `packages/cms/internal/authstore`, over the generated store operations. A family may declare one or many tables, all related to its name.

**Rationale**: The session-authentication plan (012) deliberately ships contracts only and states SQL persistence is application domain. The store specification (013) requires every feature to contribute its structures to the shared store. The user directed that families be named after their domain rather than the package or feature that introduces them, so the data is reusable and findable by future developers: `users` and `sessions` are project-wide domains, not CMS internals. The adapter stays next to its only consumer until a second consumer exists. Generated operations keep applications free of ad-hoc SQL.

**Alternatives considered**: (a) an `auth` family for sessions plus a `cms` family for users/recovery/throttling (the earlier draft) — rejected by the user: those names describe the introducing package, not the data domain; (b) one `cms` family for everything — rejected for the same reason and because sessions span applications; (c) a new shared package (`packages/authstore` or `packages/store/auth`) — rejected by YAGNI while the CMS is the only consumer; extraction is a mechanical refactor when housekeeping or the game server needs it; (d) persistence inside `packages/auth` — explicitly rejected by 012 ("the library ships no persistence implementation").

## R2 — Password hashing: bcrypt via `golang.org/x/crypto/bcrypt`

**Decision**: Hash account passwords with bcrypt (cost 12, salt generated by the library). The cost is a `Hasher` setting so tests construct the service with cost 4 for speed; production uses 12.

**Rationale**: OWASP accepts bcrypt as a password hash when the work factor is at least 10; `bcrypt.GenerateFromPassword`/`CompareHashAndPassword` are one-call, constant-time-safe APIs, and the dependency is a well-maintained part of `golang.org/x/crypto`. A tunable cost seam is the smallest thing that keeps the red-green test loop fast without changing production security.

**Alternatives considered**: (a) argon2id — OWASP's first choice but requires hand-rolled salt/parameter encoding and verification logic, more code and more room for error (KISS); (b) PBKDF2 — not recommended as the primary choice when bcrypt is available; (c) plain SHA-256 with rounds — rejected outright.

## R3 — Recovery completes with a single-use reset link; the request response is always neutral

**Decision**: `POST /forgot` validates the form; when the username and email match an account, generate a 32-byte random token, store only its SHA-256 digest with a 30-minute expiry, and email a link to `GET /reset?token=…`. The response is always the same neutral confirmation card. `GET /reset` validates the token and renders the reset form (invalid/expired tokens render the neutral invalid state); `POST /reset` sets the new password, marks the token used, revokes every session of the account, and redirects to the homepage.

**Rationale**: The specification fixes the request side (FR-017–FR-021, C2) but recovery cannot be completed without a way to set a new password. A time-limited single-use link is the OWASP-aligned completion and the only one that never emails a secret password. Storing only the digest means a store leak cannot be replayed. The reset page is a necessary consequence of the feature, not an invented destination.

**Alternatives considered**: (a) email a temporary password — rejected: transmits a reusable secret and requires extra password-strength handling; (b) require operator intervention — rejected: not self-service, contradicts "recover access"; (c) a reset code the member types — more steps for the same security, no benefit.

## R4 — Email delivery: a small `Mailer` interface in the CMS, SMTP implementation, filesystem outbox fallback

**Decision**: Define `Mailer` (`Send(ctx, Message)`), implement an SMTP sender activated by `CMS_SMTP_ADDR`/`CMS_SMTP_FROM`, and a filesystem outbox (`CMS_MAIL_OUTBOX`, default `./mail-outbox`) that writes one `.eml` file per message when SMTP is not configured. Tests use a recording fake. Recovery messages and any future transactional mail go through the interface.

**Rationale**: FR-018 requires delivery to the registered email; the project has no mail facility today. The interface keeps the account service testable, the outbox makes the full recovery flow exercisable in development without an SMTP server, and it keeps recovery secrets out of logs (the constitution forbids logging secrets). Placement inside `packages/cms/internal/mail` follows the monorepo rule that packages own implementation and avoids inventing a shared mail package before a second consumer exists.

**Alternatives considered**: (a) SMTP only — dev flow cannot complete recovery; (b) log the email — leaks reset tokens into logs; (c) a third-party mail SDK — new dependency and provider lock-in for one message type.

## R5 — Failed sign-in and recovery throttling: per-account and per-address counters in the store

**Decision**: Keep counters in a `login_attempts` table keyed by a namespaced string (`u:<canonical-username>`, `ip:<remote-address>`, `r:<canonical-username>` for recovery). A failure increments both the account key and the address key inside the same request. After `maxFailures` (5) within a `window` (15 minutes) for either key, the key is locked for `lockDuration` (15 minutes). A successful sign-in clears the account key. Stale windows are reset by the increment operation itself (`failures = 1` when `updated_at` is older than the window). All thresholds live in one exported configuration block consumed by the app.

**Rationale**: FR-013 and SC-010 require throttling that does not confirm whether a username exists. Throttling the address key closes the enumeration loophole of account-only lockout (a nonexistent username would otherwise never throttle), and clearing only the account key on success avoids locking a shared address forever. Doing the increment in SQL keeps concurrent attempts correct through the store's single-connection pool.

**Alternatives considered**: (a) account-only lockout — leaks existence and enables a targeted lockout DoS; (b) in-memory counters — lost on restart and inconsistent across instances, violating the same store contract as sessions; (c) exponential per-request sleep — no persistence and ties up handlers.

## R6 — Public POST requests are guarded by a same-origin check (login CSRF)

**Decision**: A router middleware applied to the unsafe public routes (`POST /{$}`, `POST /register`, `POST /forgot`, `POST /reset`) rejects requests whose `Origin` (or, when absent, `Referer`) is present and does not match the configured public base URL. Requests with neither header (non-browser clients, tests) pass. Authenticated state-changing routes get the session's synchronizer token from `auth.Protect` instead.

**Rationale**: The auth library's CSRF token is bound to a session, so it cannot protect the sign-in and registration forms that run without one; OWASP still requires cross-site protection for state-changing forms, and login CSRF (signing a victim into an attacker-controlled account) is the notable risk. Browser form posts always carry `Origin` or `Referer`, so checking them is sufficient and needs no extra token plumbing. Allowing absent headers keeps curl/health checks and tests working.

**Alternatives considered**: (a) a second, pre-session synchronizer cookie — new machinery and a second token lifecycle for no extra protection over same-origin checks; (b) no protection — accepted risk before 014, not acceptable once the spec's FR-011 is in force; (c) hidden per-form tokens in the store — same complexity as (a).

## R7 — Client entry: a protected minimal page, runtime embed deferred

**Decision**: `GET /client` is a protected route rendering a minimal `client.astro` page that identifies the signed-in member (username) and reserves the surface where the Director runtime will be embedded. The signed-in navigation opens it with `target="_blank"`. The runtime embed, SSO handoff, and client contents remain with the future client/server features.

**Rationale**: FR-025 requires a separate window that identifies the member and requires sign-in; the spec's Out of Scope list explicitly excludes the client window's contents. A minimal page makes the requirement testable now (unauthenticated redirect; member identity present in the opened window) and gives the client feature its landing route. The session cookie already travels with the popup because it is same-origin; no new handoff mechanism is invented.

**Alternatives considered**: (a) no page, link to a configured external URL — nothing to protect or test, and the "identifies the member" clause cannot be satisfied; (b) embed `@project-reborn/client-r26` now — large, belongs to the client/server pipeline; (c) an SSO ticket table — speculative identity handoff with no consumer (YAGNI).

## R8 — Avatars: static figure images per gender; the figure composer is deferred

**Decision**: The registration avatar box offers two static CMS-shipped images (female, male); the chosen value (`female`/`male`) is stored on the account and the personal page shows the corresponding static image. Composing real Habbo figures from the extracted part sprites, or calling an imaging service, is out of scope.

**Rationale**: The figure system lives in the client (`hh_human` casts) and needs the Director runtime and figure data; reproducing it in the CMS is a separate feature of its own. The spec requires choosing and showing an avatar, which static assets satisfy testably. The account stores the choice, so a later figure feature only changes rendering.

**Alternatives considered**: (a) compose parts in the CMS now — disproportionate complexity; (b) reference a hypothetical imaging URL — no such service exists and the page would break; (c) defer avatar display entirely — violates FR-005/FR-026.

## R9 — Game status/online count: a `status.Provider` seam with an offline default

**Decision**: Define a narrow `Provider` interface (`Snapshot(ctx) (Status, error)`, `Status{Up bool, Online int}`). The app wires a stub provider that returns the sample values clarified for the first delivery slice (a sample count and online) until a game-server integration exists, while the interface keeps the down path ready; handlers render the offline state when the provider errors or reports down. Tests inject fakes.

**Rationale**: FR-001 and SC-009 require showing status/online count and a clear offline state, while the game server does not exist. The seam is one small interface and makes both states testable; the eventual integration (HTTP call or shared store) replaces the wiring only.

**Alternatives considered**: (a) hardcode offline — FR-001's count can never be exercised or tested; (b) build a server monitor now — no server exists.

## R10 — CSRF delivery to Svelte: a meta tag plus the library's header

**Decision**: The signed-in layout renders `<meta name="csrf-token" content="[[ .CSRF ]]">`. Svelte components read it from the DOM and send it in the `X-CSRF-Token` header on `fetch` calls (the library's default header). Server-rendered forms post it as the `csrf_token` field (the library's default param).

**Rationale**: `[[ ]]` placeholders are only substituted in built HTML, never in JS bundles (templating skill gotcha), so the token must travel through markup. A meta tag is scalar, safe for `html/template` attribute escaping, available to every component without prop-drilling, and matches the library's dual header/form acceptance.

**Alternatives considered**: (a) pass the token as a Svelte prop — works only for simple scalars and risks prop serialization corruption; (b) fetch a token endpoint on mount — extra round trip and endpoint; (c) put the token in a cookie — defeats the synchronizer-token design (D7 in 012).

## R11 — Configuration: environment variables with safe defaults, cookie hardening follows the base URL

**Decision**: The CMS app reads `CMS_ADDR` (default `localhost:8080`), `CMS_BASE_URL` (default `http://localhost:8080`), `CMS_DB_PATH` (default `habbo.db`), `CMS_SMTP_ADDR`, `CMS_SMTP_FROM`, `CMS_MAIL_OUTBOX`, `CMS_HELP_URL`, `CMS_TERMS_URL`, `CMS_PRIVACY_URL`, `CMS_FAILURE_MAX`, `CMS_FAILURE_WINDOW`, `CMS_LOCK_DURATION`, `CMS_PURGE_INTERVAL`. When `CMS_BASE_URL` is `https`, sessions use the library defaults (`__Host-session`, `Secure`); when `http` (development), the app selects `session` with `WithCookieSecure(false)` because `__Host-` cookies require `Secure`, and logs a non-secret warning that production must use HTTPS.

**Rationale**: The current app hardcodes `localhost:8080`; the feature adds store, mail, and origin concerns that must be configurable without new dependencies. Deriving cookie hardening from the scheme keeps development frictionless while preserving the library's secure defaults in production. All values have safe defaults so `go run` works with no environment file.

**Alternatives considered**: (a) a config file — new parsing dependency for no current need; (b) hardcoding dev values and requiring env in production — error-prone; (c) disabling `Secure` unconditionally — ships an insecure default.

## R12 — Purge scheduling: an hourly ticker in the app entrypoint

**Decision**: Expose `CMS.Purge(ctx) (int, error)` on the public API and have `apps/cms` run a ticker (interval `CMS_PURGE_INTERVAL`, default 1h) that calls it; the goroutine stops with the server context.

**Rationale**: The session library owns purge but "the caller owns the schedule" (012). Sessions and login-attempt rows would otherwise accumulate forever. The app entrypoint owns the process lifecycle, while the wipe logic stays inside the package that holds the adapter. It is a few lines, not a background framework.

**Alternatives considered**: (a) purge on every request — hidden cost and contention; (b) never purge — unbounded growth; (c) a separate cron/job — no scheduler exists in this repo; (d) `CMS.Mount` starting its own goroutine — no context or shutdown story.

## R13 — Testing: Go end-to-end handler tests over a temp store; no JS test runner added in this slice

**Decision**: All behavior tests live in Go: `internal/account` and `internal/authstore` unit tests, and `internal/router` handler tests using `httptest`, a temporary SQLite file through `store.Open`, a fake `Mailer` that records messages, a fake `status.Provider`, and a test `astro.Resolver` returning inline `[[ ]]` templates. Frontend verification is `pnpm --filter @project-reborn/cms build` plus the templating skill's grep for surviving placeholders; the two Svelte components are thin wrappers over Go endpoints already covered by handler tests, so no vitest is added to the CMS package now; when the two Svelte components ship, `packages/cms` adds a `test` script and vitest coverage for them, satisfying the constitution's JS gate (IV).

**Rationale**: The store library is built for temp-file databases and the auth library was tested with in-memory role implementations; handler tests exercise validation, transactions, sessions, CSRF, recovery, and throttling end to end. Adding vitest would duplicate cover of two fetch wrappers and add a dependency the package does not have.

**Alternatives considered**: (a) mock the store in handler tests — loses the SQL, transaction, and constraint coverage the spec cares about; (b) add vitest now — unjustified by two thin components; revisit when a component grows real logic.

## R15 — Service and wiring layout

**Decision**: `packages/cms` gains implementation under `internal/` plus a small public option surface on the existing root package:

- `internal/account` — `Service` with `Register`, `Authenticate`, `Availability`, `UpdateMotto`, `RequestRecovery`, `ResetPassword`, plus validation, the bcrypt `Hasher`, and `BaseURL` for building reset links. It depends on `*store.Store` and on a consumer-defined `Sender` interface (`Send(ctx, to, subject, body string) error`).
- `internal/authstore` — `Store` implementing `auth.Creator`, `Validator`, `Toucher`, `Revoker`, `AccountRevoker`, `Lister`, `Purger` over `*store.Store`.
- `internal/mail` — concrete senders `SMTP` and `Outbox`, each with `Send(ctx, to, subject, body string) error`; no exported interface, consumers define their own narrow one.
- `internal/status` — concrete `Offline` provider with `Snapshot(ctx) (up bool, online int, err error)`.
- `internal/router` — consumer-defined interfaces `Mailer` and `StatusProvider` in `Deps{Resolver, Accounts, Sessions, Mailer, Status, BaseURL, Links}` plus one file per route; `Mount` in `cms.go` builds the router, the page/API `auth.Protect` closures, and the origin-check middleware.
- Public root `cms.go` options: `WithStore`, `WithBaseURL`, `WithLoginPolicy(maxFailures int, window, lock time.Duration)`, `WithMailOutbox`, `WithSMTP`, `WithStatus`, `WithLinks`, plus `CMS.Purge(ctx)`. Concrete implementations are constructed by the options, so `apps/cms` never touches `internal/`.

**Rationale**: Keeping interfaces at the consumer (`account.Sender`, `router.Mailer`, `router.StatusProvider`) is the Go-idiomatic form of dependency inversion and avoids a root↔internal import cycle. Handlers stay thin (parse → call domain → render); the account service holds all credential and validation policy; the adapter isolates SQL mapping. `auth.Protect` closures are constructed once in `Mount`, not per request.

**Alternatives considered**: (a) domain logic inside handlers — mixes HTTP and credential policy; (b) a repository interface over the store — the generated typed operations already are the narrow API (013 decision), so an extra layer is speculative; (c) public interfaces for mail/status — consumers do not need to name them because options construct the implementations and tests are in-module.

## R16 — Template error/value data shape

**Decision**: Each page handler passes a page struct (`formPage` shared by index/register/forgot/reset with `Values` and `Errors` maps or typed fields). Errors render next to their fields; entered values (except passwords) are echoed back with `[[ ]]`; passwords are never echoed. The forgot confirmation state is a boolean (`Submitted`) on the same page struct.

**Rationale**: FR-008, FR-014, FR-029 require per-field messages and retained input; the template resolver parses built HTML with `html/template`, where nested struct fields and `[[ if .Submitted ]]` blocks work directly. Passwords are never re-rendered (FR-012).

**Alternatives considered**: redirect-after-post with flash messages — would need session flash storage for a public flow and loses entered values; per-page bespoke structs — one shared `formPage` covers all four public forms.

## R17 — Styling: Tailwind utilities only, palette mapped through `tools/tw-color`

**Decision**: Every visual value is a Tailwind utility class; `global.css` stays `@import "tailwindcss"` with no custom CSS. The legacy CMS palette is translated to Tailwind CSS v4 tokens with the repository tool `tools/tw-color` (`make tw-color`, see its README) and the documentation references the tokens, never hex. The mapping is fixed in [contracts/ui.md](./contracts/ui.md#color-mapping-authoritative): document `sky-200`, paper border/shadow `mist-400`, online text `orange-500`, banner body `taupe-200`, banner border/shadow `mauve-300`, join button `lime-600`/`lime-900`/`lime-500`, login header `neutral-500`, login body `olive-400`, login card links `olive-800`, white. The common 3px bottom shadow is a Tailwind arbitrary utility over a theme variable (`shadow-[0_3px_0_var(--color-mist-400)]`), and Tailwind v4 dynamic spacing gives the signed-out width exactly (`max-w-189` = 756px).

**Rationale**: The user's palette is not part of Tailwind and `tw-color` exists precisely to map it; the user directed "use Tailwind classes always" and "use Tailwind colors for the docs". Referencing tokens keeps the docs consistent with the utility system and makes the neutral families introduced in v4 (`mist`, `taupe`, `mauve`, `olive`, verified present in the installed `tailwindcss@4.3.3` theme) explicit. Arbitrary utilities over `--color-*` variables remain Tailwind classes while deriving their value from the theme.

**Alternatives considered**: (a) raw hex in `@theme` custom properties — rejected: it introduces non-palette colors and custom CSS; (b) picking classic neutral families by eye — rejected: the tool is the authoritative mapper and reports the perceptual distance; (c) arbitrary shadows with raw hex — rejected: bypasses the palette mapping the user asked for.
